    5. Transacciones

    Las transacciones son un aspecto crucial de los SGBD que garantizan la integridad, coherencia y fiabilidad de los datos. Una transacción en SQL representa una secuencia de sentencias SQL que se ejecutan como una única unidad de trabajo, es decir todas a la vez sin interferencias (por ejemplo de otros usuarios modificando las mismas tablas/datos).

    Las propiedades fundamentales de una transacción, a menudo denominadas propiedades ACID, son Atomicidad, Consistencia, Aislamiento y Durabilidad.

    • Atomicidad: Garantiza que una transacción se trate como una unidad de trabajo única e indivisible. O bien todos los cambios realizados por la transacción se consignan en la base de datos, o bien no se consigna ninguno. Si alguna parte de la transacción falla, toda la transacción vuelve a su estado anterior.
    • Consistencia: Garantiza que una transacción lleve la base de datos de un estado válido a otro. Evita que se puedan romper las restricciones de integridad, deshaciendo los cambios en caso necesario.
    • Aislamiento: Garantiza que la ejecución de una transacción esté aislada de la ejecución de otras transacciones. El aislamiento evita las interferencias entre transacciones garantizando la consistencia e integridad de los datos.
    • Durabilidad: Garantiza que, una vez realizada una transacción, sus efectos sean permanentes y sobrevivan a cualquier fallo posterior, como una caída del sistema.

    Las transacciones se usan principalmente para asegurar la integridad de los datos, durante y después de las instrucciones. Los escenarios más comunes son:

    • Manipulación de datos.
    • Secuencia de consultas.

    1.1. Inicio y fin de una transacción

    Una transacción comienza con la primera instrucción DML que se ejecute o con la sentencia START TRANSACTION; y finaliza con alguna de estas circunstancias:

    • Una operación COMMIT; o ROLLBACK;.
    • Una instrucción DDL (como ALTER TABLE, por ejemplo).
    • Una instrucción DCL (como GRANT).
    • El usuario abandona la sesión.
    • Caída del sistema.

    Hay que tener en cuenta que cualquier instrucción DDL, DCL, así como iniciar otra transacción con START TRANSACTION;, da lugar a un COMMIT implícito (automático).Es decir, todas las instrucciones DML ejecutadas hasta ese instante pasan a ser definitivas.

    1.2. COMMIT

    La instrucción COMMIT; confirma los cambios realizados por la transacción para que sean definitivos, irrevocables. Sólo se debe utilizar si estamos de acuerdo con los cambios, conviene asegurarse mucho antes de realizar el COMMIT ya que las instrucciones ejecutadas pueden afectar a miles de registros. Esto no es un repositorio, no se guardan varios estados, sólo el último.

    Atención

    Mucho cuidado con los COMMIT implícitos por usar sentencias DDL, DCL o START TRANSACTION.

    El cierre correcto de la sesión puede dar lugar a un COMMIT/ROLLBACK dependiendo del SGBD. Conviene ejecutar explícitamente la instrucción deseada para asegurarse. En MySQL no se ejecuta un COMMIT automático en el cierre de sesión, por ejemplo.

    1.3. ROLLBACK

    ROLLBACK; regresa la BD al punto anterior al inicio de la transacción, normalmente el último COMMIT, la última instrucción DDL/DCL o el inicio de la sesión.

    Anula definitivamente los cambios, por lo que conviene también asegurarse de esta operación. Un abandono de sesión incorrecto o un problema de comunicación o una caída del sistema dan lugar a un ROLLBACK implícito.

    1.4. Auto-commit

    Algunos SGBD, como MySQL, tienen un modo llamado autocommit que hace un COMMIT automático con cada sentencia DML. Por tanto las transacciones solo funcionan si se definen específicamente con START TRANSACTION;, mientras que en otros SGBD son inherentes a las instrucciones DML.

    El modo autocommit en MySQL empieza habilitado por defecto en cada sesión aunque se puede desactivar mediante SET autocommit=0;, de este modo las sentencias DML no se confirmarán automáticamente aunque no se inicie específicamente una transacción con START TRANSACTION; y funcionará como la mayoría de SGBD. Se puede volver a activar el funcionamiento con autocommit ejecutando SET autocommit=1;.

    Los cambios en el funcionamiento del autocommit no afectan a la configuración del servidor, ni siquiera permanentemente a la del cliente; afectan sólo a la sesión actual, la siguiente vez que el cliente se conecte autocommit vuelve a estar activo. Para cambiar la configuración por defecto del servidor se debería modificar este valor en el archivo de configuración.

    Este modo de operación puede ser desconcertante si se tiene experiencia con otros sistemas de bases de datos, donde es una práctica estándar emitir una secuencia de instrucciones DML y confirmarlas (COMMIT) o deshacerlas (ROLLBACK) todas juntas.

    1.5. SAVEPOINT

    Algunos SGBD, como Oracle, MySQL o PostgreSQL, permiten definir puntos de control intermedio en una transacción con la instrucción SAVEPOINT nombre;. Esto permite deshacer los cambios realizados desde ese punto en adelante sin tener que deshacer toda la transacción. Se pueden definir varios puntos de control en una transacción, siempre que tengan nombres distintos, si se repite el nombre, el nuevo punto de control sobrescribe al anterior.

    Para volver al estado deseado se usa ROLLBACK TO nombre;. Se debe tener en cuenta que si volvemos a un punto de control, todos los puntos de control posteriores se eliminan, como se ha comentado anteriormente, las transacciones no tienen un comportamiento de historial completo como un repositorio de versiones. Otros puntos de control previos sí que se mantienen.

    Al terminar la transacción, cualquiera que sea el método de finalización, todos sus puntos de control se eliminan automáticamente. Si se desea eliminar algún punto de control para liberar memoria durante el transcurso de la transacción puede hacerse con RELEASE SAVEPOINT nombre;

    La sintaxis en SQL Server es distinta, SAVE/ROLLBACK TRANSACTION nombre;.

    1.6. Estado de los datos durante la transacción

    Recordemos que una transacción se inicia con un comando DML o START TRANSACTION. Cuando esto sucede, hay que tener en cuenta que:

    • Se puede volver a la instrucción anterior al inicio de la transacción cuando se desee (ROLLBACK).
    • También se puede volver a los puntos de control intermedios creados (ROLLBACK TO).
    • Las instrucciones de consulta (SELECT) realizadas por el usuario que inició la transacción muestran los datos ya modificados por las instrucciones DML (INSERT, DELETE, UPDATE).
    • El resto de usuarios, en cambio, ven los datos tal cual estaban antes de la transacción, de hecho los registros afectados por la transacción aparecen bloqueados hasta que la transacción finalice. Esos usuarios no podrán modificar los valores de dichos registros.
    • Del mismo modo, si otros usuarios modifican registros que no estén bloqueados tras el inicio de la transacción, el usuario que la inició no verá esos cambios hasta que la transacción finalice.
    • Tras la transacción, todos los usuarios ven los datos en el estado que quedan tras las transacciones. Los bloqueos son liberados y los puntos de ruptura borrados.

    1.7. Ejemplos

    Ejemplo 1: Transacción Simple

    Usaremos la tabla de departamentos de las unidades anteriores, borraremos todos los departamentos anteriores y crearemos uno nuevo. Después deshacemos los cambios:

    mysql> START TRANSACTION;
Query OK, 0 rows affected (0,00 sec)

mysql> DELETE FROM departamentos;
Query OK, 4 rows affected (0,00 sec)

mysql> INSERT INTO departamentos (cod_dpt, nombre_dpt, ubicacion) VALUES 
    -> ('MKT', 'Márquetin', 'Planta segunda U2');
Query OK, 1 row affected (0,00 sec)

mysql> SELECT * FROM departamentos;
+---------+-------------+-------------------+
| cod_dpt | nombre_dpt  | ubicacion         |
+---------+-------------+-------------------+
| MKT     | Márquetin   | Planta segunda U2 |
+---------+-------------+-------------------+
1 row in set (0,01 sec)

mysql> -- Anulamos los cambios
mysql> ROLLBACK;
Query OK, 0 rows affected (0,00 sec)

mysql> SELECT * FROM departamentos;
+---------+-----------------+-------------------+
| cod_dpt | nombre_dpt      | ubicacion         |
+---------+-----------------+-------------------+
| ADM     | Administración  | Planta quinta U2  |
| ALM     | Almacén         | Planta baja U1    |
| COM     | Comercial       | Planta tercera U3 |
| CONT    | Contabilidad    | Planta quinta U1  |
| INF     | Informática     | Planta sótano U3  |
+---------+-----------------+-------------------+
5 rows in set (0,00 sec)

    Con un COMMIT en lugar del ROLLBACK se hubiesen confirmado los cambios.

    Ejemplo 2: Autocommit

    Comprobamos ahora el funcionamiento del autocommit en MySQL. Primero comprobamos que el funcionamiento por defecto es con autocommit activado (las sentencias DML se auto-confirman y no se pueden deshacer)

    mysql> INSERT INTO departamentos (cod_dpt, nombre_dpt, ubicacion) VALUES
    -> ('MKT', 'Márquetin', 'Planta segunda U2');
Query OK, 1 row affected (0,01 sec)

mysql> ROLLBACK;
Query OK, 0 rows affected (0,00 sec)

mysql> -- Autocommit hace que el ROLLBACK no sea aplicable.
mysql> SELECT * FROM departamentos;
+---------+-----------------+-------------------+
| cod_dpt | nombre_dpt      | ubicacion         |
+---------+-----------------+-------------------+
| ADM     | Administración  | Planta quinta U2  |
                      [...]
| MKT     | Márquetin       | Planta segunda U2 |
+---------+-----------------+-------------------+
6 rows in set (0,00 sec)

    Lo borramos, desactivamos el autocommit y repetimos el procedimiento anterior

    mysql> -- Borramos 'MKT'
mysql> DELETE FROM departamentos WHERE cod_dpt='MKT';
Query OK, 1 row affected (0,00 sec)

mysql> -- Desactivamos autocommit, ahora todo DML necesita confirmación
mysql> SET autocommit=0;
Query OK, 0 rows affected (0,01 sec)

mysql> INSERT INTO departamentos (cod_dpt, nombre_dpt, ubicacion) VALUES
    -> ('MKT', 'Márquetin', 'Planta segunda U2');
Query OK, 1 row affected (0,00 sec)

mysql> ROLLBACK;
Query OK, 0 rows affected (0,00 sec)

mysql> -- Rollback deshace el Insert, estamos en una transacción.
mysql> SELECT * FROM departamentos;
+---------+-----------------+-------------------+
| cod_dpt | nombre_dpt      | ubicacion         |
+---------+-----------------+-------------------+
| ADM     | Administración  | Planta quinta U2  |
| ALM     | Almacén         | Planta baja U1    |
| COM     | Comercial       | Planta tercera U3 |
| CONT    | Contabilidad    | Planta quinta U1  |
| INF     | Informática     | Planta sótano U3  |
+---------+-----------------+-------------------+
5 rows in set (0,00 sec)

mysql> -- Reactivamos autocommit
mysql> SET autocommit=1;
Query OK, 0 rows affected (0,00 sec)

    En muchos SGBD el funcionamiento por defecto es así, no hay autocommit y no se necesita una sentencia específica para iniciar la transacción. No es el caso de MySQL como hemos visto.

    Ejemplo 3: Puntos de control

    Ahora vamos a insertar varios departamentos, con puntos de control intermedios y deshacer los cambios hasta un punto concreto.

    mysql> START TRANSACTION;
Query OK, 0 rows affected (0,00 sec)

mysql> INSERT INTO departamentos (cod_dpt, nombre_dpt, ubicacion) VALUES
    -> ('MKT', 'Márquetin', 'Planta segunda U2');
Query OK, 1 row affected (0,00 sec)

mysql> SAVEPOINT punto1;
Query OK, 0 rows affected (0,00 sec)

mysql> INSERT INTO departamentos (cod_dpt, nombre_dpt, ubicacion) VALUES
    -> ('VEN', 'Ventas', 'Planta tercera U2');
Query OK, 1 row affected (0,00 sec)

mysql> SAVEPOINT punto2;

mysql> INSERT INTO departamentos (cod_dpt, nombre_dpt, ubicacion) VALUES
    -> ('RRHH', 'Recursos Humanos', 'Planta cuarta U1');
Query OK, 1 row affected (0,00 sec)

mysql> ROLLBACK TO punto1;
Query OK, 0 rows affected (0,00 sec)

mysql> SELECT * FROM departamentos;
+---------+-----------------+-------------------+
| cod_dpt | nombre_dpt      | ubicacion         |
+---------+-----------------+-------------------+
| ADM     | Administración  | Planta quinta U2  |
| ALM     | Almacén         | Planta baja U1    |
| COM     | Comercial       | Planta tercera U3 |
| CONT    | Contabilidad    | Planta quinta U1  |
| INF     | Informática     | Planta sótano U3  |
| MKT     | Márquetin       | Planta segunda U2 |
+---------+-----------------+-------------------+
6 rows in set (0,00 sec)

mysql> ROLLBACK TO punto2;
ERROR 1305 (42000): SAVEPOINT punto2 does not exist

mysql> ROLLBACK;
Query OK, 0 rows affected (0,00 sec)

mysql> ROLLBACK TO punto1;
ERROR 1305 (42000): SAVEPOINT punto1 does not exist

    Como se puede observar, se puede volver a cualquier punto de control, pero una vez hecho, los puntos de control posteriores se pierden. Sí que se podría haber vuelto al punto2 y posteriormente al punto1 (o otra vez al punto2), e incluso crear otros puntos de control nuevos tras cualquier ROLLBACK TO.

    Una vez terminada la transacción todos sus puntos de control se eliminan.

    Ejemplo 4: Conflictos entre usuarios

    Para este ejemplo se necesitan 2 clientes conectados a la misma base de datos. Puedes abrir dos terminales de MySQL aunque uses el mismo usuario, por ejemplo.

    Cliente 1

    Se cambia el código de 'INF' a 'IT'.

    mysql> START TRANSACTION;
Query OK, 0 rows affected (0,00 sec)

mysql> UPDATE departamentos SET cod_dpt='IT' WHERE cod_dpt='INF';
Query OK, 1 row affected (0,00 sec)
Rows matched: 1  Changed: 1  Warnings: 0

-- Se ejecutan ahora las sentencias en el cliente2 antes del COMMIT
mysql> COMMIT;
Query OK, 0 rows affected (0,01 sec)

    Cliente 2

    Antes de confirmar la transacción en el cliente 1 consultamos los datos en el cliente 2. El código sigue mostrándose como 'INF'. Tras esto intentamos actualizar los datos. Se puede observar como los otros registros están libres, pero el registro con código 'INF' está bloqueado.

    Nota

    En MySQL los bloqueos se realizan a nivel de registro, no de tabla. Así que una transacción puede bloquear solo algunos registros y no toda la tabla.

    mysql> SELECT * FROM departamentos;
+---------+-----------------+-------------------+
| cod_dpt | nombre_dpt      | ubicacion         |
+---------+-----------------+-------------------+
                      [...]
| INF     | Informática     | Planta sótano U3  |
+---------+-----------------+-------------------+
5 rows in set (0,00 sec)

mysql> UPDATE departamentos SET cod_dpt='AD' WHERE cod_dpt='ADM';
Query OK, 1 row affected (0,00 sec)

mysql> UPDATE departamentos SET cod_dpt='???' WHERE cod_dpt='INF';

-- Se queda bloqueado aquí no avanzará hasta terminal la transacción del cliente 1
-- Tras ejecutar el COMMIT en el cliente 1 podemos seguir

mysql> SELECT * FROM departamentos;
+---------+-----------------+-------------------+
| cod_dpt | nombre_dpt      | ubicacion         |
+---------+-----------------+-------------------+
| AD      | Administración  | Planta quinta U2  |
                      [...]
| IT      | Informática     | Planta sótano U3  |
+---------+-----------------+-------------------+
5 rows in set (0,00 sec)

    ¿Que ha pasado aquí? Para empezar, el registro con código 'ADM' estaba libre, y por tanto se puede modificar sin problemas, aunque esto tampoco sería visible para el cliente 1 hasta terminar su transacción. En cambio, registros con código 'INF' o 'IT' están bloqueados, por lo que no se pueden modificar. El cliente 2 se queda bloqueado hasta que el cliente 1 termine su transacción o se supere el tiempo de espera configurado en el SGBD, en cuyo caso se produciría un error.

    Tras finalizar la transacción del cliente 1, se liberan los bloqueos y, si no ha expirado, se ejecuta la operación bloqueada en el 2. En este caso, como el registro 'INF' ha sido modificado, a 'IT', la operación del cliente 2 se ejecuta pero no encuentra registros con código 'INF' y no se modifica nada. Si se hubiese hecho un ROLLBACK en el cliente 1, o el UPDATE del cliente 2 filtrase por 'IT' en lugar de 'INF', se habría modificado el registro y sería '???'.

    Esto se usa para evitar que se apliquen cambios simultáneos entre varios clientes que entren en conflicto entre ellos, pero permitiendo cambios en la misma tabla siempre que no entren en conflicto.

    Nota

    Independientemente de los bloqueos, ningún cambio realizado por una transacción es visible para otros usuarios hasta que termine. Del mismo modo, los cambios realizados por otros usuarios no son visibles durante la transacción. Esto se usa también en transacciones solo de lectura (sin DML) para evitar que los datos cambien mientras se realizan las consultas.
